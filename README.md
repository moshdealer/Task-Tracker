# Task Tracker

REST API для управления задачами внутри команд. Сервис поддерживает ролевую модель, историю изменений задач, комментарии, кеширование списков задач в Redis и агрегированный SQL-отчёт по команде.

## Возможности

- регистрация и аутентификация по JWT
- создание команд и управление участниками с ролями `owner`, `admin`, `member`
- создание, фильтрация и обновление задач
- защита от потери изменений с помощью версии задачи
- история изменений и комментарии
- кеширование списка задач на 5 минут с инвалидацией после изменений
- статистика команды: задачи по статусам, топ-3 исполнителя по выполненным задачам `done`, среднее время выполнения и количество комментариев
- автоматическое применение миграций при старте
- OpenAPI-спецификация всех endpoint'ов и моделей
- структурированные JSON-логи

## Стек и архитектура

- Go 1.27
- MySQL 8.4
- Redis 7.4
- Docker и Docker Compose
- Swagger/OpenAPI 3.0

Приложение реализовано как модульный монолит: один Go-процесс обслуживает единый HTTP REST API, работает с одной схемой MySQL и использует Redis только для кеширования.

```text
cmd/                  точка входа приложения
internal/
  auth/               регистрация, вход, JWT
  teams/              команды, участники и роли
  tasks/              задачи, история и кеш списка
  comments/           комментарии к задачам
  analytics/          SQL-отчёт команды
  platform/           конфигурация, MySQL, Redis, HTTP и логирование
migrations/           встроенные SQL-миграции
api/openapi.yaml      OpenAPI-спецификация
tests/integration/    интеграционный тест отчёта
```

## Быстрый запуск через Docker Compose

### Требования

- Docker с поддержкой Compose
- свободные порты `8080`, `3306` и `6379` либо другие значения в `.env`

### 1. Подготовить конфигурацию

```bash
cp .env.example .env
```

Перед запуском замените в `.env` как минимум `JWT_SECRET`, `MYSQL_PASSWORD` и `MYSQL_ROOT_PASSWORD`. Для `JWT_SECRET` используйте длинное случайное значение.

### 2. Запустить приложение

```bash
docker compose up --build
```

После запуска API доступен по адресу `http://localhost:8080`. MySQL и Redis публикуются только на loopback-интерфейсе хоста.

При старте приложение:

1. подключается к MySQL
2. применяет все ещё не выполненные миграции
3. подключается к Redis
4. запускает HTTP-сервер

Запуск в фоне и просмотр логов:

```bash
docker compose up --build -d
docker compose logs -f app
```

Остановка контейнеров:

```bash
docker compose down
```

Именованные тома MySQL и Redis при этом сохраняются. Чтобы удалить их вместе с данными, выполните `docker compose down -v` только если данные больше не нужны.

## Конфигурация

Приложение читает необязательный файл `.env` из текущего каталога. Переменные окружения имеют приоритет над значениями файла.

| Переменная | Обязательность | Значение по умолчанию / пример | Назначение |
|---|---:|---|---|
| `APP_ENV` | нет | `local` | окружение: `local`, `dev`, `stage`, `prod`, `test` |
| `SHUTDOWN_TIMEOUT` | нет | `10s` | время на корректную остановку HTTP-сервера |
| `HTTP_HOST` | нет | `0.0.0.0` | адрес HTTP-сервера |
| `HTTP_PORT` | нет | `8080` | порт HTTP-сервера |
| `HTTP_READ_HEADER_TIMEOUT` | нет | `5s` | тайм-аут чтения заголовков |
| `HTTP_WRITE_TIMEOUT` | нет | `10s` | тайм-аут записи ответа |
| `HTTP_IDLE_TIMEOUT` | нет | `60s` | тайм-аут keep-alive соединения |
| `DATABASE_URL` | да | `task_tracker:change-me@tcp(mysql:3306)/task_tracker?parseTime=true` | DSN подключения к MySQL |
| `DB_MAX_OPEN_CONNS` | нет | `25` | максимум открытых соединений с MySQL |
| `DB_MAX_IDLE_CONNS` | нет | `5` | максимум простаивающих соединений |
| `DB_CONN_MAX_LIFETIME` | нет | `30m` | максимальное время жизни соединения |
| `JWT_SECRET` | да | — | секрет подписи JWT |
| `JWT_TTL` | нет | `24h` | срок действия JWT |
| `REDIS_URL` | да | `redis://redis:6379/0` | адрес Redis |
| `LOG_LEVEL` | нет | `info` | уровень логов: `debug`, `info`, `warn`, `error` |
| `MYSQL_PORT` | только Compose | `3306` | порт MySQL на хосте |
| `MYSQL_DATABASE` | только Compose | `task_tracker` | имя базы данных |
| `MYSQL_USER` | только Compose | `task_tracker` | пользователь MySQL |
| `MYSQL_PASSWORD` | только Compose | `change-me` | пароль пользователя MySQL |
| `MYSQL_ROOT_PASSWORD` | только Compose | `change-root-password` | пароль `root` MySQL |
| `REDIS_PORT` | только Compose | `6379` | порт Redis на хосте |

Значения длительности задаются в формате Go, например `500ms`, `10s`, `5m`, `24h`.

## Локальный запуск без контейнера приложения

Для локальной разработки можно запустить MySQL и Redis в Docker, а Go-приложение — на хосте:

```bash
docker compose up -d mysql redis
```

В локальном `.env` адреса контейнеров нужно заменить на опубликованные порты хоста:

```dotenv
DATABASE_URL=task_tracker:change-me@tcp(127.0.0.1:3306)/task_tracker?parseTime=true
REDIS_URL=redis://127.0.0.1:6379/0
JWT_SECRET=replace-with-a-long-random-secret
```

Затем запустите приложение:

```bash
go run ./cmd
```

## Миграции

SQL-миграции находятся в каталоге [`migrations`](migrations) и встраиваются в бинарный файл приложения. При каждом старте автоматически выполняются все ожидающие `up`-миграции. Повторный запуск безопасен: уже применённые миграции пропускаются.

Новая миграция оформляется парой файлов с последовательным номером:

```text
migrations/000002_description.up.sql
migrations/000002_description.down.sql
```

Приложение не выполняет `down`-миграции автоматически.

## Аутентификация

Регистрация и вход доступны без токена. Для остальных запросов передавайте JWT в заголовке:

```http
Authorization: Bearer <token>
```

При отсутствующем, повреждённом или просроченном токене API отвечает `401 Unauthorized`.

## Роли и доступ

| Действие | `owner` | `admin` | `member` |
|---|:---:|:---:|:---:|
| Просмотр команды и её задач | да | да | да |
| Создание задачи | да | да | да |
| Редактирование любой задачи команды | да | да | нет |
| Редактирование созданной им задачи | да | да | да |
| Изменение статуса назначенной ему задачи | да | да | да |
| Приглашение участника | да | да | нет |
| Приглашение администратора | да | нет | нет |
| Изменение роли участника | да | нет | нет |
| Просмотр статистики команды | да | да | нет |

Роль `owner` назначается создателю команды и не может быть выдана через приглашение или изменена обычным запросом смены роли. Исполнитель задачи должен состоять в той же команде.

## API

Полное описание параметров, моделей ответов и ошибок находится в [`api/openapi.yaml`](api/openapi.yaml). Файл можно импортировать в Swagger Editor или другой совместимый OpenAPI-клиент.

| Метод | Путь | Описание | Доступ |
|---|---|---|---|
| `POST` | `/api/v1/register` | регистрация | публичный |
| `POST` | `/api/v1/login` | вход и получение JWT | публичный |
| `POST` | `/api/v1/teams` | создание команды | JWT |
| `GET` | `/api/v1/teams` | команды текущего пользователя | JWT |
| `POST` | `/api/v1/teams/{id}/invite` | добавление существующего пользователя | `owner`, `admin` |
| `PUT` | `/api/v1/teams/{id}/members/{user_id}/role` | смена роли `member`/`admin` | `owner` |
| `POST` | `/api/v1/tasks` | создание задачи | участник команды |
| `GET` | `/api/v1/tasks` | список задач с фильтрами | участник команды |
| `PUT` | `/api/v1/tasks/{id}` | частичное обновление задачи | по ролевым правилам |
| `GET` | `/api/v1/tasks/{id}/history` | история изменений | участник команды |
| `POST` | `/api/v1/tasks/{id}/comments` | добавление комментария | участник команды |
| `GET` | `/api/v1/tasks/{id}/comments` | список комментариев | участник команды |
| `GET` | `/api/v1/teams/{team_id}/stats` | SQL-отчёт команды | `owner`, `admin` |

Допустимые статусы задачи: `todo`, `in_progress`, `hold`, `done`, `cancel`.

### Примеры запросов

Ниже предполагается, что API запущен на `http://localhost:8080`.

#### Регистрация

```bash
curl -i -X POST http://localhost:8080/api/v1/register \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "owner@example.com",
    "password": "strong-password",
    "name": "Владелец команды"
  }'
```

#### Вход

```bash
curl -s -X POST http://localhost:8080/api/v1/login \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "owner@example.com",
    "password": "strong-password"
  }'
```

Ответ:

```json
{
  "token": "<jwt>"
}
```

Для следующих примеров сохраните полученное значение:

```bash
TOKEN='<jwt>'
```

#### Создание команды

```bash
curl -i -X POST http://localhost:8080/api/v1/teams \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Backend"}'
```

#### Приглашение пользователя

Приглашаемый пользователь уже должен быть зарегистрирован.

```bash
curl -i -X POST http://localhost:8080/api/v1/teams/1/invite \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "member@example.com",
    "role": "member"
  }'
```

Успешный запрос возвращает `204 No Content`.

#### Создание задачи

```bash
curl -i -X POST http://localhost:8080/api/v1/tasks \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "team_id": 1,
    "title": "Подготовить релиз",
    "description": "Проверить миграции и документацию",
    "status": "todo",
    "assignee_id": 2
  }'
```

#### Список задач

Параметр `team_id` обязателен. Необязательные фильтры: `status`, `assignee_id`, `limit`, `offset`.

```bash
curl -s 'http://localhost:8080/api/v1/tasks?team_id=1&status=todo&assignee_id=2&limit=20&offset=0' \
  -H "Authorization: Bearer $TOKEN"
```

Списки кешируются в Redis на 5 минут. Ключ кеша учитывает команду, фильтры и пагинацию; после создания или изменения задачи кеш соответствующей команды инвалидируется.

#### Обновление задачи

Обновление частичное, но поле `version` обязательно. Передавайте версию из последнего ответа API:

```bash
curl -i -X PUT http://localhost:8080/api/v1/tasks/1 \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
    "version": 1,
    "status": "in_progress"
  }'
```

При успешном изменении версия увеличивается. Если другой запрос уже изменил задачу, устаревшая версия приводит к `409 Conflict`; клиенту нужно получить актуальную задачу из списка и повторить осознанное изменение. Каждое фактическое изменение сохраняется в истории со старыми и новыми значениями.

#### История и комментарии

```bash
curl -s http://localhost:8080/api/v1/tasks/1/history \
  -H "Authorization: Bearer $TOKEN"

curl -i -X POST http://localhost:8080/api/v1/tasks/1/comments \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"content":"Готово к проверке"}'

curl -s http://localhost:8080/api/v1/tasks/1/comments \
  -H "Authorization: Bearer $TOKEN"
```

#### Статистика команды

```bash
curl -s http://localhost:8080/api/v1/teams/1/stats \
  -H "Authorization: Bearer $TOKEN"
```

Пример ответа:

```json
{
  "team_id": 1,
  "tasks_by_status": {
    "todo": 3,
    "in_progress": 2,
    "hold": 0,
    "done": 7,
    "cancel": 1
  },
  "top_assignees_last_30_days": [
    {
      "assignee_id": 2,
      "name": "Участник команды",
      "closed_tasks": 5
    }
  ],
  "average_close_hours": 18.75,
  "comments_count": 12
}
```

Отчёт строится одним SQL-запросом для указанной команды. Статус `cancel` означает отмену, а не выполнение: такие задачи остаются в распределении по статусам, но не входят в топ-3 исполнителей и среднее время выполнения. Топ учитывает только задачи `done`, закрытые за последние 30 дней; среднее время выполнения рассчитывается по всем задачам `done` за всё время.

## Ошибки

Ошибки возвращаются в едином формате:

```json
{
  "error": "описание ошибки"
}
```

Основные HTTP-коды:

- `400 Bad Request` — некорректные параметры или тело запроса
- `401 Unauthorized` — отсутствующий или недействительный JWT
- `403 Forbidden` — пользователь известен, но у него недостаточно прав
- `404 Not Found` — сущность не найдена или недоступна текущему пользователю
- `409 Conflict` — конфликт данных, повторное добавление или устаревшая версия задачи
- `500 Internal Server Error` — внутренняя ошибка сервера

## Тестирование

Проверка сборки всех обычных пакетов:

```bash
go test ./...
```

Обязательный интеграционный тест SQL-отчёта имеет build tag `integration` и требует доступную базу MySQL. Он применяет миграции, создаёт уникальные тестовые данные в локальной базе и удаляет их после выполнения.

```bash
TEST_DATABASE_URL='task_tracker:change-me@tcp(127.0.0.1:3306)/task_tracker?parseTime=true' \
  go test -tags=integration ./tests/integration -run TestTeamStats -count=1 -v
```

Флаг `-count=1` отключает использование кешированного результата, а `-v` выводит рассчитанные метрики отчёта и результаты всех проверяемых сценариев. Если в `.env` заданы другие `MYSQL_USER` или `MYSQL_PASSWORD`, замените их в строке подключения. Используйте эту команду только для локальной базы разработки, не для production-базы.
